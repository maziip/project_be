3.2 wrapper 필수

wrapper는 gradle 본체가 아니라 "정해진 버전의 gradle을 내려받아 실행해 주는 작은 실행기"다. 프로젝트에 같이 commit된다. 네 파일이다.

  • gradlew: 맥·리눅스용 실행 스크립트. 우리가 치는 ./gradlew가 이것
  • gradlew.bat: 윈도우용. 같은 일
  • gradle/wrapper/gradle-wrapper.jar: 실제로 다운로드·실행하는 작은 자바 프로그램
  • gradle/wrapper/gradle-wrapper.properties: 어느 버전을 어디서 받을지. 우리는 gradle-9.7.1-bin.zip

./gradlew build를 치면: 스크립트가 jar 실행 → jar가 properties를 읽음 → ~/.gradle/wrapper/dists/에 9.7.1이 있으면 쓰고 없으면 다운로드 → 그 gradle에 build를 넘김.

왜 중요한가. 팀원마다, CI 러너마다 gradle 버전이 달라도 ./gradlew만 치면 모두 9.7.1로 빌드한다. 그래서 CI 워크플로에 "gradle 설치"가 없다. 로그의 Downloading .../gradle-9.7.1-bin.zip 줄이 그 증거였다. 시스템에 brew install gradle로 깐 gradle은 gradle init 한 번에만 쓰고 그 뒤로는 쓰지 않는다.

4.3 용어

  • 브랜치: commit 줄기의 이름. main은 기준 줄기, BE-001A는 티켓 작업 줄기. Unity로 치면 씬을 복제해서 실험하는 것과 비슷하되, 나중에 합칠 수 있다.
  • origin: 원격 저장소의 별명. origin/main은 "마지막으로 GitHub와 통신했을 때 본 원격 main".
  • HEAD: 지금 내가 서 있는 commit. 보통 현재 브랜치의 마지막 commit.
  • merge: 브랜치를 main에 합치기. 우리는 일반 merge(commit 이력 보존)를 쓴다. squash는 여러 commit을 하나로 뭉치는데, 기록이 해시를 증거로 쓰므로 안 쓴다.
  • revert vs reset: revert는 취소 commit을 추가(안전, 이력 남음). reset은 이력을 지움(이번 주 안 씀, 당분간 쓰지 말 것).

5. GitHub와 gh 필수

Git은 내 컴퓨터의 도구, GitHub는 그 저장소를 올려 두는 웹 서비스다. gh는 GitHub를 터미널에서 다루는 명령어(GitHub CLI)다. 웹에서 클릭으로 하는 일을 글자로 한다.

5.1 PR(Pull Request)

"내 브랜치를 main에 합쳐 달라"는 요청서. 코드 차이(diff), 설명, 리뷰 댓글, CI 결과가 한 화면에 모인다. 이번 주 PR #1(BE-001), PR #2(BE-001A)를 열었다. PR 설명은 docs/pr/티켓.md에 네 항목으로 쓴다: ① 구현 내용 ② 설계 결정과 이유 ③ 테스트 방법과 결과 ④ 한계와 확인받고 싶은 것.

PR 설명에서 두 번 지적받은 것. "AI 안내에 따라 했다"는 이유가 아니다. 리뷰어가 알고 싶은 것은 내가 왜 이렇게 골랐는지와 실제로 돌린 명령과 그 출력이다. 파일 경로, 명령, 출력 한 줄 인용이 있으면 통과한다.

6. GitHub Actions와 CI 필수

CI(Continuous Integration): 코드를 올릴 때마다 자동으로 빌드·테스트해서 깨졌는지 확인하는 장치. Unity Cloud Build와 같은 개념. GitHub Actions는 그걸 돌려 주는 GitHub의 서비스.

6.1 워크플로 파일 한 줄씩

name: CI                       # 이 지시서의 이름. PR 화면에 표시

on:                            # 언제 돌릴지
  push:
    branches: ["main"]         # main에 commit이 올라오면
  pull_request:
    branches: ["main"]         # main을 향한 PR이 열리거나 갱신되면

jobs:                          # 무엇을 돌릴지
  build:                       # 잡 이름(자유). Ruleset에서 이 이름을 검사 항목으로 씀
    runs-on: ubuntu-latest     # 우분투 리눅스 컴퓨터를 빌려서
    steps:                     # 순서대로
      - uses: actions/checkout@v6         # 1) 저장소 내려받기 (남이 만든 기능 = uses)
      - uses: actions/setup-java@v5       # 2) JDK 설치
        with:                             #    그 기능에 넘기는 옵션
          java-version: '21'
          distribution: 'temurin'
      - run: ./gradlew build              # 3) 명령 직접 실행 (= run)
  • 러너: 매번 새로 빌리는 깨끗한 컴퓨터. 내 맥에 깐 건 거기 없다. 그래서 JDK는 설치하고, gradle은 wrapper가 받아 오니 안 깐다.
  • uses vs run: uses는 GitHub 마켓의 기성 기능(액션)을 가져다 씀. run은 터미널 명령을 그대로 침.
  • @v5: 액션의 버전. 한국어 문서는 @v4였는데 실행해 보니 deprecated 경고가 떠서 v5로 올렸다. 문서보다 실제 실행 결과를 믿는다.

6.2 언제 도는가

상황CI이유
PR 없이 작업 브랜치에 push안 돔on의 두 조건 모두 해당 없음
main 대상 PR 열기돔pull_request
PR 열린 상태에서 그 브랜치에 push돔PR이 갱신되어 pull_request 다시 발생
PR 병합돔main에 commit 생김 → push

6.3 Ruleset(브랜치 보호) 필수

CI는 결과를 보여 줄 뿐 막지는 않는다. 막으려면 저장소 설정(Settings → Rules → Rulesets)에서 규칙을 건다. 우리 main 보호 규칙: (1) PR을 통해서만 main에 합칠 수 있다 (2) build 검사가 통과해야 합칠 수 있다 (3) main 삭제 금지 (4) 강제 push 금지. 처음 만들 때 "대상 브랜치"를 안 넣어서 아무 데도 안 걸린 상태였다. 규칙은 "무엇을"과 "어디에" 둘 다 있어야 한다.

이번 주 실험의 의미. 초록불만 봐서는 CI가 일하는지 모른다. 테스트를 일부러 깨뜨려 push → 빨간불 → revert → 초록불. 이 세 번이 "실패를 잡는다"는 증거다. 앞으로 어떤 자동화든 일부러 실패시켜 보는 것이 검증 방법이다.

7. YAML 필수

docker-compose.yml과 ci.yml 둘 다 YAML이다. 앞으로 Spring 설정(application.yml)도 YAML이다. 규칙은 넷뿐이다.

  1. 맵(키: 값): name: CI. 콜론 뒤 공백 필수. 콜론 앞엔 공백 없이.
  2. 중첩은 들여쓰기: 스페이스 2칸씩. 탭 금지. 같은 깊이는 같은 칸수.
  3. 리스트: - 항목. steps: 아래 각 스텝, branches: ["main"]의 대괄호도 리스트.
  4. 문자열 따옴표: 보통 생략 가능. 숫자처럼 보이는 걸 문자열로 두고 싶으면 '21'처럼 감싼다.

이번 주 오류는 전부 "맵이어야 할 곳에 리스트" 또는 "들여쓰기 한 칸 차이"였다. 오류 메시지의 must be a mapping은 "여기 맵이 와야 한다", must be a array는 "여기 리스트가 와야 한다"는 뜻이다.

8. Docker와 Compose 알아두기

개념은 docker-1단계-개념.html에 있으니 여기서는 명령만 적는다. 2주 차 이후 MySQL이 필요할 때 다시 쓴다.

명령 (docker/ 폴더에서)뜻
docker compose up -d컨테이너 기동(백그라운드). 재기동도 이것
docker compose ps상태 확인
docker compose logs mysql로그. ready for connections가 보이면 준비됨
docker compose down컨테이너 종료·삭제. 볼륨(데이터)은 남음
docker compose configyml 문법 검사

비밀번호는 docker/.env에 있고 git에 올라가지 않는다(.gitignore). 흐름: .env → compose가 ${VAR}를 치환 → 컨테이너 환경변수 → MySQL 첫 초기화 때 사용.

10. 우선순위 정리

다음 주 월요일까지 손에 익혀야 하는 것 (외우기가 아니라, 보지 않고 칠 수 있게).
  1. git status --short → git add → git commit -m → git push. 그리고 status 색 읽기.
  2. git switch -c 브랜치로 시작해서 gh pr create → gh pr checks --watch → gh pr merge --merge로 끝나는 티켓 한 바퀴.
  3. ./gradlew build 결과 마지막 줄 읽기. 실패하면 어느 태스크가 왜 실패했는지 찾기.
  4. YAML 들여쓰기 규칙 넷.
설명할 수 있으면 되는 것. wrapper가 뭔지와 왜 CI에 gradle 설치가 없는지. toolchain과 JAVA_HOME의 차이. CI가 언제 도는지(6.2 표). Ruleset이 CI와 어떻게 다른지.
지금은 몰라도 되는 것. Kotlin DSL 문법, JUnit 상세, Docker 내부 구조, gradle 캐시·concurrency 같은 CI 최적화, git reset/rebase.
